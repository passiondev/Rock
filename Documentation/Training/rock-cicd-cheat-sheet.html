The one rule Branch from the default branch and open your PR into it. That is whatever GitHub shows you when you open the repo, and whatever .github/pr-test-environments.json names as baseBranch — the two always agree. Any other base branch and the robot silently ignores you: no error, no test site.

The loop

1. Find the file (press t) → 2. Edit, commit to a new branch → 3. Open PR, base = the default branch → 4. Add rock:start → 5. Wait ~30 min → 6. Open the URL in the robot's comment → 7. Get a review, merge → 8. Add rock:destroy when done

Labels you press

rock:startBuild my branch, give me a site
rock:autoRebuild on every push
rock:stopShut down, keep files
rock:destroyDelete it entirely

Labels the robot sets (don't touch)

queued building deploying deployed stopped failed

deployed = your site is up; the URL is in the PR comment. failed = open Logs in that comment and find the red step.

No VPN needed. These open from anywhere, on a phone too. staging and pr-4 have real Let's Encrypt certificates, so no warning. A brand-new PR environment starts on a self-signed placeholder until the weekly renewal issues one for its host name. That warning is expected and safe to click through for *.rock-dev.connect.passion.team only.

Expect a slow first load, one to two minutes, while Rock runs its migrations and warms its caches. Every load after that is well under a second. Reload once, and wait it out, before reporting anything.

It goes cold again after 20 minutes of nobody touching it, so a site that was fast before lunch is slow after. That is normal and is not your change breaking. If you are about to show someone, load it a few minutes early.

Cleanup: partly on you

  • Merged PR → environment destroyed
  • Closed, not merged → stopped, files kept
  • Anything else → runs until you destroy it. Nothing reaps on a timer.

Before you say it's broken

  1. Is the PR's base branch the repo's current default branch?
  2. Every page 500ing? Open staging. If it's broken too, it isn't your change.
  3. Is the file in your PR's Files changed tab?
  4. Changed LESS? Recompile: Admin → CMS → Themes. Then hard-refresh.
  5. Still stale? Hard-refresh (Cmd-Shift-R).

Not everything is a file

HTML Content block text, page names and routes, Lava in block settings, workflows and reports live in the database. You change those in the Rock admin UI on the live site. This pipeline only moves files. Unsure? Ask before you start.

Test environments are not safe for data

The database is shared and gets reset. No email, no texts, no payments, no scheduled jobs. A migration in your PR changes that shared database for everyone. Don't build a demo on data you need next week.

Two ways to cause real damage

The repo is public. Rock is open source and our fork is too. Never commit a password, connection string, API key, or any export with member names, emails, phones or giving data. Deleting it later does not remove it from history. Tell DevOps so the credential gets rotated.

A migration in your PR touches the shared database. Tell DevOps before you apply rock:start. It runs against the sandbox everyone else is using, and you can't take it back.

Trunk branch: the repo default, and what staging builds from. It is renamed at every Rock upgrade — read it, do not memorise it Base branch is set by .github/pr-test-environments.json Never open a PR against develop. It is our older line, not a mirror of upstream Verified 2026-08-10
