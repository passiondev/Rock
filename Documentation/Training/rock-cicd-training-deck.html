00Why any of this exists

Everyone here has a MacBook. Rock only builds on Windows.

That single sentence is the reason this pipeline exists. Everything else follows from it.

The wall

Rock is ASP.NET 4.5 WebForms on the .NET Framework — not .NET Core. It compiles with MSBuild and Visual Studio build tools, which exist only on Windows. There is no macOS build. There is no Linux build. Not "it's harder" — it does not run.

The way around it

GitHub rents us a clean Windows machine for the length of a build. It compiles Rock, packages the site, and installs it on a server in Google Cloud. You do all of your work in a browser and never install Windows.

So the pipeline is not process for its own sake. It is the only way this team can ship Rock at all.

01Git in five minutes

A branch is a copy of everything that you cannot break.

Repository

The folder holding every Rock file, plus the full history of every change ever made. Ours is passiondev/Rock.

Branch

Your own copy of all of it. Edit freely — nobody else sees your branch and nothing you do there can affect the live site.

Commit

One save point, with a note saying what you changed and why. History is a list of commits, so anything can be undone.

Two things make git feel strange at first, and both are actually the point: nothing is ever overwritten — old versions stay reachable forever — and you work on a copy, then ask for it to be merged. There is no "save to the server."

01Git in five minutes

A pull request is the request, the conversation, and the button.

"Pull request" is a bad name. Read it as: please pull my changes into the shared branch.

What it is

  • A proposal to merge your branch into a shared one
  • A page showing exactly which lines you changed
  • Where review, comments, and approval happen
  • Where the robot reports whether your change builds
  • Where you press the buttons that give you a test site

The tabs you'll use

  • Conversation — description, comments, the robot's status
  • Files changed — the actual diff. Red removed, green added. Always look here before asking for review.
  • Checks — the build, live, with logs
  • Labels (sidebar) — your buttons
01Git in five minutes

Branching strategy: one trunk, many short branches.

Why short branches

A branch that lives for two days merges cleanly. A branch that lives for two months collides with everything and becomes a project of its own. Small and frequent beats big and careful.

Why one trunk

There is exactly one branch that represents "what we run." Everything merges there and staging always shows it. No guessing which branch is real.

02The fork

We didn't write Rock. We forked it.

Spark Development Network SparkDevNetwork/Rock the open-source original
→
Our fork passiondev/Rock everything theirs + everything ours
→
Our servers Google Cloud built from our fork only

A fork is a full copy of someone else's repository that you own, with the family tree intact — so you can still pull their updates down and still send fixes back up.

What's ours

On the trunk, 68 files upstream doesn't have — and 63 of them are this pipeline: the workflows, the deploy scripts, the docs, the tests. Five are product code, all one Form Builder feature.

Our long-standing custom blocks — check-in, scheduling, RSVP, finance, CMS — are 78 files under RockWeb/Plugins/org_passion and team_passion. They are on the older develop branch, not on the trunk. Reconciling those two is the next piece of work and the top item on the open-items list.

Why fork instead of starting clean

Rock is roughly two gigabytes of application we get for free and did not have to build. Forking means we keep receiving their security fixes and features instead of freezing in time.

02The fork

A fork is a two-way street. Both directions have rules.

Down: their work into ours

The clean reference point is not a branch of ours at all — it is Spark's tag 18.4.1, fetched from the upstream remote. That tag is what we diff against to see exactly what is ours and what is theirs.

Our develop branch is not a clean mirror, despite the name. It carries 276 files under RockWeb/Plugins/, 78 of them ours, where upstream's tag carries 2. It is history we still need, not a reference copy.

Never open a PR against develop.

Up: our work into theirs

If we fix a genuine bug in core Rock, we can contribute it back. The repo has a separate PR template for that — open the PR with ?template=upstream-contribution.md and it asks for what Spark's maintainers need.

The public consequence

Because Rock is open source, our fork is public. Anything committed is visible to the entire internet, permanently, including after you "delete" it in a later commit. No passwords, no connection strings, no exports with member names, emails, phone numbers, or giving data. If it happens, tell DevOps immediately so the credential gets rotated — deleting it is not enough.

03Version branches

The trunk is named after the Rock version it runs.

●───●───◆───●───●──▶passion-18.4.1Spark's tag 18.4.1 (◆, July) + this pipeline
     ╲
      ●───●───●──▶developdiverged Jan 2026 — holds our 78 plugin files

Read the fork from the left: we share history with Spark up to January, they carried on to the 18.4.1 tag in July, and our trunk continues from that tag. develop is the older line that kept going in parallel.

Why the version is in the name

A Rock upgrade is not a normal change — it moves thousands of files at once. Naming the trunk after the version makes the answer to "what is production running?" a thing you can read, not a thing you ask about.

The cost of not doing that is already in this repo: develop is really Rock 19.0.3 and staging is really Rock 17.6.1. Neither name says so — you have to open a source file to find out.

What the pipeline builds today

passion-18.4.1 is the repository's default branch, so it's what you land on when you open the repo, and it's what staging builds from.

Production runs Rock 18.4 at its core and was last touched by hand, in July. Pointing this pipeline at it is the next step, and it happens with DevOps in the room — not from a laptop.

03Version branches

How the next upgrade happens.

You will not do this. It's here so the branch names you'll see next year make sense.

  1. Fetch from upstream so we have Spark's tags for the new release.
  2. Cut passion-18.5 from the upstream tag for that release.
  3. Replay our own work onto it and fix what conflicts.
  4. Point .github/pr-test-environments.json at the new branch — one file decides which base branch gets test environments.
  5. Make it the repo default. Deploy it to staging. Live on staging until it's boring.
  6. Deploy to production. Retire the old trunk.

The practical consequence for you: the branch you target changes on every upgrade. Don't memorize passion-18.4.1. Read the default branch, or read that one config file.

04Making changes

Labels are buttons. That's the whole control panel.

GitHub has no "deploy" button we can add, so we used the one thing on a PR that anyone can click.

You press these

rock-test:startBuild my branch and give me a site
rock-test:autoRebuild it every time I push
rock-test:stopShut it down, keep the files
rock-test:destroyDelete it entirely

The robot sets these — don't touch them

queued building deploying deployed stopped failed

They're a status light. deployed means your site is up and the URL is in the PR comment.

Cleanup: merging the PR destroys its environment · closing it without merging only stops it and keeps the files. Nothing else reaps anything on a timer — if you're done with an environment, add rock-test:destroy yourself.

04Making changes

Why a pull request, even for a one-word typo.

It's the only way to get a test site

Test environments are built per PR. No PR, no build, no site, no way to see your change before it's live.

It proves the thing compiles

One stray character in a C# file takes the whole site down. The build catches that in CI instead of on the live site at 9am Sunday.

It's the record

Six months from now, "why is this like this?" has an answer: the PR, the discussion, and who approved it.

It makes undo cheap

A merged PR is one revertible unit. Edits made straight on a server are archaeology.

One real exception. A lot of what looks like "editing the website" in Rock is not a file at all — HTML Content block text, page names and routes, Lava in block settings, workflows, reports. Those live in the database and you change them in the Rock admin UI on the live site. This pipeline only moves files. If you're unsure which side of that line you're on, ask before you start.

05Why GitHub builds it

What "build" actually means for Rock.

Not a website that gets uploaded. An application that gets compiled — roughly 25 minutes of work on a machine none of us owns.

The compiled Obsidian block JavaScript is not stored in the repo — it only exists after a build. That is exactly why "just copy the files up" doesn't work: half the site isn't in the files.

05Why GitHub builds it

Four reasons it can't be your laptop.

1 · It physically can't

MSBuild and the .NET Framework targeting packs are Windows-only. A Mac cannot produce these binaries at all.

2 · "Works on my machine" stops existing

The runner is a brand-new, identical Windows box every single time. Nobody's stale local install can make a build pass or fail.

3 · Credentials stay out of laptops

Database passwords and cloud keys live in GitHub secrets and are only ever read by the build. They never land on anyone's machine, and they're never printed in a log.

4 · It runs while you don't

25 minutes of compiling happens on someone else's computer. You close the tab and come back to a working URL.

The trade: you can't get a 10-second feedback loop. Budget ~30 minutes from label to live site, and batch your changes accordingly.

Things a test environment is not

The database is shared and gets reset — don't build a demo on data you need. No email, no texts, no payments, no scheduled jobs. A migration in your PR changes that shared database for everyone. The URLs themselves are public HTTPS, so no VPN is needed to open one.

06Three doors

Merging deploys staging. Nothing merges to production.

There is no branch you can push, and no label you can add, that reaches the live site.

Staging — automatic, and safe

Merge your PR and ~30 minutes later it's live on staging for the whole team. It's a separate site on the test server, on the sandbox database. It cannot see production data and cannot take production down.

Documentation-only commits are skipped — a 30-minute Windows build per typo fix isn't a good trade.

Production — two locks

  1. Someone opens Actions and runs Deploy Production deliberately. The default run is a dry run that reports its plan and changes nothing.
  2. It builds, then stops and waits for a named reviewer to approve — after the build, so nobody is asked to approve a commit that doesn't compile. Not even a repo admin can skip that gate.

What it does on the server, and what it refuses to do

Backs up the current site → stops the app pool → copies the new files → starts it → polls until the site answers. It never mirrors: uploaded content, logs, and the cache are server-owned and cannot be deleted by a deploy. And CI never writes production's connection string — so the production database password doesn't have to exist as a secret here, and a deploy can't point production at the wrong server.

08Questions you're about to ask

Anticipated questions.

Do I have to learn command-line git?
No. Everything in this deck happens in a browser: edit, commit, PR, label, review, merge. A local clone is optional and only pays off if you're editing dozens of files at once.
I merged and my change isn't on the live site.
Correct and expected. Merging deploys staging. Production is a separate, deliberate run that someone has to start and a named reviewer has to approve.
Can I break production by doing this wrong?
Not by merging, pushing, or labelling. The only path to production is a manual workflow run behind an approval gate, and its default mode changes nothing. The realistic risks are a migration in your PR (it hits the shared sandbox database for everyone) and committing something secret to a public repo.
Why does it take thirty minutes?
About 25 of it is genuinely compiling Rock and building two separate Vue workspaces on a fresh Windows machine. The rest is packaging, uploading, installing, and waiting for Rock to apply its migrations on first request. It is not queueing.
Why did nothing happen when I added the label?
Almost always the base branch. Test environments are only built for PRs targeting the branch named in .github/pr-test-environments.json. Anything else is silently ignored — no error, by design of GitHub, not by choice.
08Questions you're about to ask

And the harder ones.

Someone needs a fix live in twenty minutes. What actually happens?
Because Rock compiles our custom blocks at runtime, an operator can copy two files onto the server — with a drift check, a hash-verified backup, and automatic rollback on mismatch. It's operator-only, it's the mechanism recent urgent fixes actually used, and it exists so you can ask for it rather than attempt it.
How do we roll back?
Run Deploy Production again with the previous good commit — rolling back is the same operation as rolling forward, which is the point. If you need it faster than a build, the previous site is still on the VM under C:\RockBackups\production\.
Was this pipeline working before today?
Parts of it were reporting green while being broken — the test VM had been off for three months, the build was looking for Visual Studio in a folder that no longer existed, build failures were being forced green, the compiled Obsidian block JavaScript was never built, and the deploy was overwriting the very theme files people were trying to test. All five are fixed, with tests that fail if they come back. There's a written list of what's still open.
What if GitHub is down?
We can't build. Production keeps serving — nothing about a running site depends on GitHub. The operator hot-deploy path also doesn't need it.
Why is my change not showing even though the build was green?
Check that the file is actually in your PR's diff and on the right path. If it's LESS, Rock's theme compiler has to recompile it (Admin → CMS → Themes). If it's an HTML Content block or a page setting, it was never a file — it's a database record you change in the admin UI.
09Where we go from here

Four things, and then it's yours.

Everyone

  1. Confirm you can sign in to passiondev/Rock, that 2FA is on, and that you can add a label to a PR.
  2. Read Parts 0–2 of the training doc, then ship one real change end to end — a typo is a perfect first PR.

DevOps

  1. Install the command-queue agent on the production VM, together, so the last step of the production path is proven.
  2. Create the production environment with required reviewers, and get the certificate renewal green.

Take with you: the one-page cheat sheet, and Documentation/Local-Engineering-Training-Edit-Test-and-Deploy.md in the repo — the long version, including nine specific traps and what to do about each. The separate open-issues list is for DevOps.

The pipeline's job is to make a change boring. If any part of it still feels like a risk, that's a bug — tell me.
